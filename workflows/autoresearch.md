# Auto Research：有边界的自主研究

规则入口：[[AGENTS#Auto Research 与多 Agent 协作|AGENTS · 自主研究]]。本流程调度 [[workflows/ingest|Ingest]]、[[workflows/query|Query]]、[[workflows/brainstorm|Brainstorm]] 与 [[workflows/lint|Lint]]，服务文献阅读和 idea 探索。它是一套执行协议，尚非后台服务。

## 一轮的约定

用户可以只给探索兴趣，不必先有成熟问题。主 Agent 从索引和主题页整理本轮约定并告知用户，在已有授权内继续执行，不为普通选文逐篇询问。

| 项目 | 开始前写清什么 |
| --- | --- |
| 目标与模式 | 探索模式产出机制/问题地图；聚焦模式核查一个具体疑问。两者均允许没有新 idea。 |
| 范围 | 模块、选定的一级子方向及要理解的问题；列出本轮暂不扩展的范围。 |
| 数量边界 | 默认每个选定子方向初筛不超过 12 篇，核心选读目标约 5 篇、最多 5 篇，定向查新补读最多 2 篇，讨论最多 2 轮。少读有理由，多读不得悄悄加量；用户给出其他上限时从其指令。 |
| 总量与资源 | 多方向须同时列出方向、模块和全轮总额，以及去重后的正文阅读上限与并发安排；按方向逐批完成闭环。时间或 token 上限仅在用户给出或运行环境实际提供时记录，不虚报精确资源预算。 |
| 权限 | 轮内可自主检索公开原文、新增不可变 Raw、维护相关 Wiki、派同模型 subagent 与做检查；费用、外部发布、实验或无关配置变更不属于本轮。 |
| 停止与交付 | 知识变化、被关闭/保留的问题、关键反证、建议用户亲读的少量原文位置、未完成项和下一步；完成本轮即停。 |

“约 5 篇”是覆盖有意义机制差异的选读规模，不是填满数额的要求。没有足够相关且可读的论文时少读并说明；新增补读占其独立上限。同一论文跨方向只计一次全局正文阅读，同时标记它支持哪些方向。已经读过的论文可复用，新增版本和实质补读仍说明工作量。

完整任务约定、候选队列、分配、完成状态、恢复点及Git检查点集中在`maintenance/research/<轮次>.md`；具体边界见[[workflows/structure|目录规则]]。主题页和[[wiki/overview|总览]]只留简短状态、研究结果和维护记录入口，不重复长期累加派发流水。只在实际开始一轮时创建有内容的记录；临时提取、初稿及完整Agent对话留获准临时区。`wiki/log.md`记录完成的实质操作，不承担任务队列。旧轮次记录在授权整理时搬移，本次仅改规则不执行。

## 从综述引用选择论文

1. 阅读当前相关主题和 S001 对应章节，核对参考文献条目及它在正文承担的论证角色；记录 S001 章节、PDF 页码和参考文献编号。不能仅凭参考文献标题判断方法。
2. 按“读它有望澄清什么”选择：机制代表、不同前提/路线、对照或反例、评测边界。优先覆盖差异，避免五篇都重复同一套路；理由逐篇写明。
3. 查找作者、会议/期刊或原始预印本渠道，核对标题、作者、标识符、版本和全文可用性。综述引用若指向博客、系统文档或标准，按实际来源类型登记，不伪装成论文凑数。
4. 初始核心选择来自 S001 引用。Brainstorm 的查新可以追索综述之外的新工作及近义机制，只要服务本轮问题并占补读预算；若用户限制只读综述引用，则遵守限制并相应收窄查新结论。
5. 候选记录至少含身份/URL、综述定位、选择或排除理由、全文状态、所属方向及是否重复。元数据核对与摘要初筛不等于 Ingest；重要网页信息进入知识前保存原始快照。

## 派发与共享写入

**总协调者负责验收和调度；论文 subagent 完成自己负责的摄入与更新。** 不要求主 Agent 逐篇重做分析，也不把审核变成只看摘要。

| 角色 | 工作与交付 |
| --- | --- |
| 总协调者 | 确定轮次边界，维护全局论文身份/来源 ID/写入所有权，分配并发资源，检查交付，组织跨模块综合。 |
| 模块负责人 | Harness 或 Optimization 的选文、方向内比较、共同证据整理和内部 Brainstorm；协调本模块任务，将结果交总协调者。只有一个模块或工作量小时可由总协调者兼任。 |
| 论文 subagent | 同主 Agent 模型；查找并核读一篇论文，完成唯一论文页、主题整合、相关索引和日志、局部检查，返回 [[workflows/ingest#Subagent 交付与验收\|交付包]]。后续修订仍找原负责人。 |
| 构思/审查 subagent | 用固定证据独立分析，审查机制、构思和新颖性；按 [[workflows/brainstorm\|Brainstorm]] 交付，不直接并发改共享主题。 |

派发每篇前，给出问题、综述引用定位、来源ID、已确认身份、材料类型、唯一主归属/交叉方向、分类后的Raw/来源页路径及代码/网页等附件位置、可写文件、预算、交付要求。目录词表和根路径解析按[[workflows/structure|目录规则]]，不让各subagent默认平铺或自建不同分类。身份未核实时先返回核对结果；来源ID只由总协调者分配，失败或撤销的已分配ID不回收。

所有子任务继承或显式使用主 Agent 当前模型，不为节省资源改成其他模型；头脑风暴首轮只传共同证据和任务约束，不传其他人的初稿。用任务说明传递必要规则，不能因隔离上下文而丢失 Vault 约束。

共享文件按以下顺序操作：

1. 论文 subagent 可并行读原文和写自己获分配的论文页/新 Raw；其他人不写这些路径。跨模块发现同论文时合并任务，由一个负责人交付，另一个模块复用。
2. 完成分析后提交待整合要点与将修改的共享文件，状态记为“已读待整合”。总协调者在全库范围授予一次共享写入时段；两个模块不能各自发出互不知情的许可。
3. 获得时段的 subagent **重读共享文件当前内容**，再整合主题、修正双向链接、更新索引与日期，做局部 Lint，并准备简短日志草稿。索引标明实际阅读和待验收状态，不提前记完成日志。不得用早先完整副本覆盖他人新内容。Obsidian 操作也使用统一时段，不能让多个任务同时控制同一窗口。
4. 返回文件清单、证据变化和检查结果，释放时段，进入“待验收”。发现问题时派原负责人修补；会改变关键判断的疑点交独立审查者回读原页。实质验收通过后，原负责人再取得短写入时段，追加正式摄入日志、更新完成状态并返回收尾确认，主 Agent 核对后结束该任务。
5. 子任务失败或中断时先确认其已停止写入，再交接所有权；读取最新文件与持久状态后接续。未整合或未验收项不能算完成，其他独立方向可继续。

这是一项调度纪律，不宣称已经部署文件锁。主 Agent 可调度一个维护 subagent 处理跨模块最终整合，但所有写者仍使用同一个共享写入队列。多人同时开启的独立聊天若没有共同协调者，就不共享写权限；不要让两个聊天各自把自己当作总协调者。

## 一轮怎样运行

1. **盘点与选文：**从已有知识出发，形成任务约定和带理由的候选，统一排重后派发同模型论文 subagent。
2. **逐篇摄入：**执行 Ingest；模块负责人检查关键理解、证据边界和维护交付，不因文件生成就算完成。
3. **方向内综合：**用问题、机制、前提、评测条件和未解释之处分组比较。必须指出哪些判断改变、哪些只是补充；条件不齐时不排分数榜。
4. **独立讨论与定向核查：**固定本批共同证据，执行 Brainstorm 首轮。将分歧转成原文核查或查新任务，必要时在补读预算内再做 Ingest；有效反证可关闭候选。
5. **修订与跨模块综合：**用补充证据做第二轮修订，相关跨方向/跨模块问题合入该轮。同一批候选总计最多两轮；只比较已有证据支持的接口和差异，缺少另一侧证据时保留待核查。两轮已用尽时只整合现有判断。
6. **写回、验收和交付：**知识进唯一来源页与相关主题，操作状态进维护记录。逐批核对材料分流、目录可查、镜像主归属和跨方向唯一性；Overview已混合多个大段比较/问题/队列时评估拆分，不能只追加正文。运行局部Lint和受影响的阅读验收，交付理解变化与亲读页段，不倾倒Agent聊天。

单个方向在目标已回答、候选被已有工作覆盖、相关全文不可获得、或预算用尽时结束并记录理由。修订后既没有新增证据，也没有预算内可执行的具体核查时，可以提前结束；只有暂缺新证据但存在明确核查任务时，先在剩余预算内执行。不可获取的单篇先尝试合法公开版本或换入预算内的相关候选；不要因一篇失败放弃其余任务。任务中断时保留进度，不把未完成工作包装成正常收敛；一轮结束不会自行开启下一轮或改成定时任务。

## Harness 与 Optimization 的组织方式

默认采用**一个总协调者 + 两个逻辑模块负责人 + 按需派发的论文/讨论 subagent**。负责人不必同时常驻；当并发名额有限时按模块和方向分批调度，给论文阅读任务留出名额。不要让层层负责人占满名额后等待无法启动的下级任务。一个模块试跑时可简化为总协调者直接派论文 subagent。

本库现有的一级选读单位是以下 13 类；更细的二级导航不自动各开一批：

| 模块 | 一级子方向及当前知识入口 |
| --- | --- |
| Harness（6 类） | [[wiki/harness/Overview#循环与工作流\|循环与工作流]]、[[wiki/harness/Overview#上下文与记忆\|上下文与记忆]]、[[wiki/harness/Overview#工具、MCP 与技能\|工具、MCP 与技能]]、[[wiki/harness/Overview#编排\|编排]]、[[wiki/harness/Overview#Hooks 与中间件\|Hooks 与中间件]]、[[wiki/harness/Overview#验证\|验证]] |
| Optimization（7 类） | [[wiki/optimization/Overview#架构基础\|架构基础]]、[[wiki/optimization/Overview#数据与环境合成\|数据与环境合成]]、[[wiki/optimization/Overview#预训练与中期训练\|预训练与中期训练]]、[[wiki/optimization/Overview#微调\|微调]]、[[wiki/optimization/Overview#Agentic Reinforcement Learning\|Agentic RL]]、[[wiki/optimization/Overview#On-Policy Distillation\|On-Policy Distillation]]、[[wiki/optimization/Overview#自我演化\|自我演化]] |

若用户选择全部一级子方向，核心选读为最多 65 个方向名额，去重后的独立论文数可能更少；按默认上限计算最多初筛 156 个方向候选名额，另有最多 26 个定向补读名额，总正文阅读上限最多 91 篇，实际去重后登记。不是一次启动 65 个 Agent，也不是必须读满 91 篇。用户只启动其中一部分时，仅计算对应范围。

模块内部先阅读、比较并完成首轮独立分析；有相关交叉问题时，将跨模块审查合入第二轮修订。若内部已用完两轮，跨模块只整合已有判断，新增争议保留为下一轮待核查项，不再追加讨论或补读。跨模块检查的问题包括：运行时保存的状态怎样进入训练样本；运行时判断能否支撑训练反馈；外部技能/经验与参数更新如何比较；性能变化能否归因于模型、harness 或预算。这些是本库的分析问题，不是预先成立的缺口。

## 并发与 Git 检查点

启动时读取实际可用的并发上限，预留主 Agent，按空闲名额派发阅读/审查任务；完成一个再补一个，不预先创建全部 65 个任务。模块负责人可阶段性承担职责，不额外常驻挤占阅读名额。共享文件和 Obsidian 操作仍串行。

Git仅由总协调者操作：先记录当前分支、HEAD与已有改动；规则和轮次约定形成启动检查点，验收通过的论文按批次提交，模块/跨模块综合再提交。提交期间暂停共享文件写入，防止已审查版本与暂存版本不一致；各论文私有页仍可在不纳入本次暂存范围时继续。每次提交前检查diff、来源完整性与链接，显式暂存本轮文件；Raw不做换行转换，PDF按二进制处理，验证暂存原件与归档字节一致。保留已有用户改动，不盲目`git add .`，不自动推送或改写历史。中断检查点须诚实标未完成。提交记录放轮次维护记录，日志按实质操作而非每个commit记账；用户只授权规则修改时，不额外写Wiki或轮次文件。

本轮用户限定仅在当前项目工作，临时材料统一存 `.research-tmp/` 并由 `.gitignore` 排除；这是通常使用系统临时目录的本轮例外。所有 subagent 遵守同一范围。
